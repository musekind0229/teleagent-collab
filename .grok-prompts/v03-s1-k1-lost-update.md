## 问题（基线仍在）

`src/framework/durable_api.py`：

1. 实例锁 + 整库快照写回：两个**独立进程**交错 `submit` 会丢 Goal（A/B 先读同一库，后写覆盖先写）。
2. `_read_json` 损坏/解码失败返回 `None`，会被当成空库覆盖原件。
3. 文件不存在才应初始化；损坏、无权读、格式不兼容必须分别报错并**保留原件**。

同类风险请扫：预算 / 所有权 / outbox 等旁路账本（同目录或相关模块）。**已安全的不要重写**；有同类漏洞一并修。

## 必须选一种方案（写进 commit message）

任选其一并强制落地：

- **单写者服务**，或
- **事务存储**，或
- **覆盖「读取—校验—修改—保存」全过程的跨进程锁**

硬约束：

- 不能只在写文件时加锁。
- 不能用未刷新、未检查版本的旧内存快照去更新。
- **仅有 atomic replace 不够**（解决不了丢更新）。
- 若选事务存储：考虑状态与 outbox 原子提交。
- 若保留文件存储：说明跨文件操作的崩溃恢复与对账。
- **Windows fcntl 留给下一刀**；本刀 Linux（fcntl/flock）即可，不要假装 Windows 已搞定。

## 验收（必须有可重复测试）

1. 两独立进程交错 submit 两个 Goal → **两个都在**。
2. 冲突的所有权/预算变更 → **最多一个成功**。
3. 损坏 / 不兼容打开后 → **原件不被改写**。
4. 中断后能恢复或明确报错（不要静默空库覆盖）。

建议把并发测试放在 `src/` 下可 `PYTHONPATH=src python3 -m unittest ...` 或现有测试风格里跑通。
